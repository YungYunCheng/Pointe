**Admin 可編輯，其餘唯讀**

| 功能 | 說明 |
|---|---|
| 單位總覽 | 330 戶樓層堆疊，依狀態篩選 |

**車位是先到先得。** 登記時有空位就配出，額滿依登記時間排候補。配位的讀取與寫入在同一筆交易裡——兩個人同時登記最後一個車位，只有一個會拿到。

### 3.3 名單管理 LeadsCrm
**使用者：** BM 主要，Admin 全權

| 功能 | 說明 |
|---|---|
| 七階段管線 | 新詢問 → 已回覆 → 已約看 → 已看房 → 已送件 → 成交／流失 |
| 逾時警示 | 新詢問 1 小時、已回覆／已看房 48 小時、已送件 24 小時 |
| 帶看行程 | 讀排程資料，兩邊同步 |
| 漏斗數據 | 各階段人數、來源成交率、流失原因 |
| **重複申請偵測** | Email／電話已在檔案裡直接擋 |
| 相似度標記 | 姓名相似加聯絡方式部分吻合 → 標記待判斷 |
| 拒絕聯絡 | CASL 退訂標記 |

**重複偵測的分界很重要：**

Email 或電話完全相同 → **硬擋**。Gmail 有正規化（`a.b+x@gmail.com` 和 `ab@gmail.com` 是同一個信箱）。

姓名相似度 70% 以上 → **標記，不自動拒絕，要人填理由**。

後者是刻意的。同姓在移民社區極常見，自動用姓名相似度拒絕會系統性打到少數姓氏被幾千個家庭共用的族群。在 Alberta 人權法下，那個結果本身就是問題，不管當初的規則是什麼意圖。而且**「系統說不行」在收到投訴時不是一個站得住腳的答案**。

單靠姓名永遠不會觸發，必須同時有聯絡方式部分吻合。

### 3.7 協議庫 Agreements（新）
**Admin 上傳與核准，PM 使用**

| 功能 | 角色 | 說明 |
|---|---|---|
| 上傳版本 | Admin | PDF 或 Word，25 MB 上限 |
| 檔案雜湊 | 系統 | 同樣位元組換標籤再傳會被擋 |
| 標記生效 | Admin | 核准前不能使用 |
| 版本取代 | 系統 | 每份協議同時只有一個生效版本 |
| 撤回 | Admin | 不刪除，已簽的照樣有效 |
| 下載 | PM | 位元組原樣輸出，附雜湊標頭 |
| 發給租客 | PM | 記錄哪一版給了誰 |
| 完備度檢查 | 全部 | 缺哪幾份，租約缺了會擋 |

**系統不產生協議。** Admin 上傳律師核定的檔案，那個檔案原樣送到租客手上。

理由很窄：**生成的條款可能無效，而且讀起來跟有效的一樣專業**。要確定租客簽的就是律師核定的，唯一辦法是那兩個是同一個檔案。

租金、押金、起租日**放在附信裡，不合併進文件**，並在發出當下拍快照——下個月調價改不掉這個租客當初被告知的數字。

### 3.11 會計 Accounting
**使用者：** Accounting 與 Admin 可過帳，PM 唯讀**

複式記帳，21 張表，49 個端點。分四個畫面。

**總覽**

| 功能 | 說明 |
|---|---|
| 現金與應收應付 | 營運帳戶餘額、租客欠款、廠商應付 |
| **信託帳戶檢查** | 1020 必須等於 2100 + 2110，不等變紅 |
| 損益 | 本期收入與費用，淨營運收入 |
| 欠租帳齡 | 未到期／1-30／31-60／60 天以上 |

**押金是信託負債，不是收入。** Alberta RTA 規定押金存信託帳戶並生息，錢是租客的。把押金記成收入會讓年度數字很好看，然後退租時沒錢可退——這是小房東最常見的翻車方式。

**租金與 AR**

| 功能 | 說明 |
|---|---|
| 收費排程 | 每筆一行，收租日上限 28 號 |
| 租金跑批 | 可重跑，同期間不會重複 |
| 按日計算 | 月中搬進搬出自動算，算式存在收費單上 |
| 收據 | 對應到特定收費單，多收的進預收租金 |

收租日上限 28 號是因為**設 30 號的排程會安靜跳過二月**，年底才會發現。

**帳單與 AP**

| 功能 | 說明 |
|---|---|
| 廠商管理 | 預設科目、付款條件 |
| 發票草稿 | 草稿不進總帳 |
| 核准過帳 | 核准才產生分錄 |
| 重複偵測 | 廠商加發票號唯一索引 |
| 付款 | 部分付款支援，不得超額 |

**交易搜尋**

一個搜尋框跨整個總帳。廠商、租客單位、科目、備註、**金額**都能搜。輸入數字會比對到分——「那筆 1,847 的付款」不用記得日期也找得到。

**銀行對帳**

| 功能 | 說明 |
|---|---|
| 對帳單上傳 | 貼 CSV，含檔案留存 |
| 自動配對建議 | 金額相同且日期相近 |
| 逐行配對 | 每一行都要有歸屬 |
| 期間結算 | 結餘要對到分才能結 |
| 期間鎖定 | 結算後拒絕新過帳 |

**「差一點點也算對完」是差額變成永久且查不到的原因。**

對帳單用貼 CSV 不是解析 PDF——瀏覽器解析銀行 PDF 是猜測包裝成功能，在對帳這裡猜錯比手打還糟。

**修訂機制**

| 功能 | 說明 |
|---|---|
| 草稿編輯 | 未過帳的自由改 |
| 已過帳修訂 | 沖銷原分錄加過帳新分錄，兩筆都留 |
| 版本號 | 文件保留編號，版本遞增 |
| 必填原因 | 沒有理由不能修訂 |
| 下限保護 | 不能改到低於已付金額 |
| 變更日誌 | 記錄異動欄位，AI 補一句人話 |

**不用刪掉重來，也不用重新輸入付款紀錄。**

**設定**

押金利率由 AI 查證提案、附出處與信心度，**會計確認才生效**。利率按年份存，跨年持有的押金每年按當年利率累計。

## 四、租客端

公開網站與住戶專區，全站中英雙語，各 191 組字串。語言跟著租客走——偵測瀏覽器語言，也記住他選過的。

| 頁面 | 功能 |
|---|---|
| 首頁 | 即時空房、公設、車位現況 |
| 房型 | 依格局顯示空房與現行租金，鏡像戶型合併 |
| 社區環境 | 三棟樓與共用設施 |
| 預約看房 | 真實可用時段，30 分鐘 |
| 線上申請 | 六步驟，草稿邊填邊存 |
| 住戶專區 | 報修、通知、租金、文件 |
| 聊天 | 全站可用，攔截規則與收件匣同一套 |

**三件這個網站主動說出口的事：**

**車位不足寫在首頁。** 222 個車位對 330 戶。這會流失一些詢問，但**簽約後才發現沒車位的租客有充分理由抱怨，簽約前就知道的沒有**。

**所有費用在送出申請前揭露**，不是核准後。Alberta 的押金上限本來就是一個月租金，寵物押金還算在裡面，根本沒有可以留到後面說的數字。

**申請表不問家庭組成。** 只問「總共幾個人住」，而且說明是因為居住人數上限的規定。家庭狀況、國籍、宗教、年齡、收入來源都是受保護特徵，一個都沒有。

「我有服務動物」勾了會直接免除寵物押金和月費——不用租客自己爭，也不用先揭露障礙才問得到答案。

**報修表單先問「有沒有安全疑慮、漏水、沒暖氣熱水」**，答是就給電話叫他打過來。表單照樣送出留紀錄，但不會讓正在漏水的案子安靜排在隊伍裡。

## 五、AI 現在能做什麼

八個任務，全部在伺服器端執行。

| 任務 | 用在哪 | 能自行送出？ | 需要權限 |
|---|---|---|---|
| inbox_draft | AI 收件匣 | 僅 12 種查詢意圖 | inbox.manage |
| intake_question | 合約組裝 | 否，只填表 | lease.sign |
| entry_notice | 現場作業台 | 否，核准後才送 | entrynotice.manage |
| parking_advice | 出租後台 | 否，給專員的建議 | parking.allocate |
| report_narrative | 會計月報 | 否，會計核准 | accounting.reports |
| change_narrative | 會計變更日誌 | 否，補充說明 | accounting.post |
| interest_rate | 會計設定 | 否，會計確認才生效 | accounting.post |
| tenant_chat | 租客聊天 | 是，但攔截規則之外才行 | 公開，依 IP 限流 |

### 全部在伺服器端

三個理由，照嚴重程度排：

**API key。** 從瀏覽器呼叫，key 會進打包檔——任何人打開開發者工具就拿得到。

**稽核。** 送到租客手上的草稿，應該追得到是哪個請求、哪個人、哪個時刻。從筆電發出的呼叫什麼都不留。

**提示詞。** 放伺服器是一份可以審閱和修改的東西；放瀏覽器就是「那個使用者上次載入的版本」。

呼叫端只能說要做什麼、提供事實，**不能用系統的 key 送任意指令給模型**。

### 四條界線

**不決定要不要送出。** AI 負責分類和起草，送不送由寫死的規則決定。出事時「為什麼這封送出去了」必須能用規則編號回答，不是「模型認為可以」。

**不寫任何協議文字。** 協議是 Admin 上傳的檔案。改版後連範本欄位偵測和文件轉檔兩個任務都拿掉了——那兩個是為了「產生文件」而存在的。

**不說任何金額。** 租金押金費用由系統組出逐字送出。會計月報更嚴格：數字用 SQL 從已過帳分錄算好，連同推導方式一起交給模型，並明確要求不准重算。

**不設定會影響金錢的參數。** 押金利率由 AI 查、附出處、標信心度，但要人按確認才生效。**AI 給一個看起來合理的錯誤利率，330 筆押金全部算錯，而且要等到有人退租才會發現。**

### 六條硬性攔截

跑在任何 AI 呼叫之前，員工收件匣和租客聊天都適用。關鍵詞中英文都有，因為租客兩種語言都會用。

| 規則 | 攔什麼 | 為什麼是規則不是判斷 |
|---|---|---|
| R-101 | 收入、AISH、信用、保證人、資格 | 收入來源是受保護特徵，自動回覆會變成差別待遇的書面證據 |
| R-102 | 輪椅、無障礙、服務犬、合理調整 | 服務動物不是寵物，套用寵物政策等同拒絕調整 |
| R-103 | 種族、宗教、小孩、婚姻、國籍 | 同 R-101，稽核只記規則編號不複製內容 |
| R-104 | 律師、RTDRS、驅逐、投訴、求償 | 爭議中的往來就是證據 |
| R-105 | 租約條款、保留單位、折扣、議價 | 具約束力的承諾需要人 |
| R-106 | 漏水、沒暖氣、沒熱水、火災、瓦斯 | 僅租客聊天，回覆辦公室電話不試著回答 |

### 事實層與校驗

AI 能回答的一切都來自即時房源資料組成的文字區塊。草稿產生後還會校驗：**任何不在那個區塊裡的金額，會讓這則回覆降級為人工審核**。

回應格式中 `missing_info` 是必填欄位。租金沒設定時，AI 只能說「確認後回覆你」，不能估。

### AI 不被允許做、目前也沒在做的事

- 判斷誰有資格承租
- 閱讀或判讀信用、收入文件
- 給名單排優先順序
- **判定兩個申請人是不是同一個人**（相似度是提示，決定權在人）
- 撰寫或改寫任何協議條款
- 定價或議價
- 核准文件、扣款、退款或任何過帳
- 設定利率或任何影響金錢的參數
- 把維修工單標成加急

## 六、需要優化的地方

### 6.1 前端尚未接上 API（最重要）

170 個端點寫好了、邏輯也對，但十四個工具還是各跑各的，資料在瀏覽器。

**這代表簽約鎖、車位排隊、會計過帳在多人環境下都不成立。** 兩個人同時記一筆收款，兩個瀏覽器互相看不見。

資料層 `web/src/lib/store.js` 已經寫好，`RESOURCES` 把 storage key 和端點並排列出。接的順序：登入 → 出租後台 → 會計 → 其餘。

### 6.2 後端仍在跑 SQLite

compose 已接好 Postgres、schema 也寫好了，但 `db.js` 開的還是檔案。要換 driver，並把 immediate transaction 改成 `SELECT ... FOR UPDATE`。

330 戶的量 SQLite 撐得住，但**兩個容器同時寫一個檔案不行**。要橫向擴充就得換。

### 6.3 沒有寄送服務商

外寄佇列建好了（Resend + Twilio 的實作也寫好了），但沒有 key。訊息會排隊、標記逾期、發告警，就是送不出去。

設 `RESEND_API_KEY` 就能寄信；簡訊要 Twilio 三個變數。**沒有 key 時佇列會停住並說明，不會假裝送出去了。**

### 6.4 密碼雜湊用 scrypt

現在用 scrypt，上線前應改成 Argon2id。

### 6.5 證據與協議存在本機磁碟

`api-data` volume 裝的是押金扣款的證據照片，現在還加上律師核定的協議檔案。**容器換到別台機器就沒了。** 應該移到物件儲存。

這個 volume 的備份優先度現在比之前高很多。

### 6.6 稽核工具用瀏覽器輪詢

只在頁面開著時看得到變動。API 端已經在每次寫入時記錄，這個工具應該改成讀 API。

### 6.7 名單與聯絡人是兩套資料

同一個人詢問、簽約、續約會出現三次。應該合併。

### 6.8 沒有影子模式

架構文件寫過：上線前讓 AI 全程跑但不送出，兩到四週用來量誤判率。值得做。

### 6.9 沒有降級訊息

AI 掛掉時應該送出固定的「已收到，同事會盡快回覆」。現在什麼都不會送。

### 6.10 預約時段已經是真的，但確認回覆沒接前端

公開回覆端點寫好了（`/api/public/confirm/:token`），租客那一側的頁面沒做，目前靠人工標記。

## 七、缺少的功能

### 7.1 必須有才能上線

**沒有律師核定的協議檔案。** 協議庫是完整的機器，圍著十一個空欄位轉。**沒有租約，什麼都不能簽。** 首頁會擋紅框提醒。

**Alberta 的數字尚未確認。** 押金上限、退款期限、通知期、入內通知時數、365 天調漲規則、押金利率。全部是各檔案開頭的具名常數，一處一改。

**沒有隱私政策。** 租客網站收集姓名、聯絡方式、上傳文件，沒有連到任何政策。

**第三方揭露未載明。** 租客訊息會送到 AI 服務商。在 PIPA 下這屬於揭露行為，必須寫進隱私政策。

**沒有資料保留期限。** PIPA 要求明訂並由排程執行。名單、訊息、申請、稽核目前無限期累積。建議：名單 12 個月、訊息 3 年、租約 7 年、稽核 7 年。

**住戶專區登入是替身。** 前端目前任何 email 密碼都能進；後端的真實登入已經寫好，等接上。

**沒有 TLS。** production 模式下 session cookie 帶 `secure`，走純 HTTP 不會送出去，登入會失敗但看起來像密碼錯——這個很容易誤判。

### 7.2 會安靜流失金錢

**續約沒有介面。** API 到期前 30 天建任務、也檢查了 365 天規則，但沒有畫面顯示。**留住租客遠比找新的便宜。**

**整備期沒有追蹤。** 搬走到重新上架之間是純空置損失，現在沒人在量。`turnover` 狀態存在，沒有東西用它。

**帶看結果沒有回饋到定價。** 一戶帶看十二次沒人申請，那是在告訴你事情。目前沒人在聽。

### 7.3 會計的空白

**GST 申報。** 1210 和 2300 有在記，申報本身不存在。

**折舊。** 1500 和 1510 存在，沒有東西過帳。

**業主報表與分配。** 沒做。

**遷出與會計還沒真正串起來。** 押金結算在營運作業台算，信託帳戶在會計，兩邊各自存在瀏覽器。接 API 之後才會通。

### 7.4 次要

- 廠商入內通知沒有回連到維修工單
- 租客網站沒有房源照片或平面圖
- 沒有手機專用的帶看流程（頁面本身是響應式的）
- 電子簽名沒接（目前是寄檔案、人工標記已簽）

## 八、建議順序

### 第一批：現在

| 項目 | 為什麼是現在 |
|---|---|
| 取得律師核定的租約 | 沒有它，整套系統跑不完一次完整流程 |
| 接 API（登入、後台、會計） | 沒接等於單機版，鎖和併發都是假的 |
| 確認 Alberta 數字 | 押金利率尤其重要，會影響每一筆退款 |
| 接寄送服務商 | 所有通知現在都送不出去 |

### 第二批：上線前

Postgres、Argon2id、TLS、隱私政策與第三方揭露、證據移到物件儲存、住戶專區登入、確認回覆頁、降級訊息。

### 第三批：上線後三個月

續約介面、整備期追蹤、資料保留排程、影子模式、遷出與會計串接、稽核改讀 API。

### 第四批：有數據之後

帶看結果回饋定價、GST 與折舊、業主報表、名單與聯絡人合併、房源照片、電子簽名。
