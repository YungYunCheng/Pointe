## 0. 自動化邊界（一句話版本）

| 可以自動送出 | 必須人工 |
|---|---|
| §4.1 表列的事實查詢 | 其他所有情況 |
| 看房／簽約的**時段**排定、改期、取消、提醒 | 租約文件的釋出 |

排程可以自動，是因為它只動行事曆，不產生金錢或法律承諾，而且錯了可以改期。租約文件不能自動，是因為送出即不可逆。

## 1. 系統目標

| 目標 | 衡量方式 |
|---|---|
| 首次回覆時間 < 5 分鐘（全時段） | 中位數回覆延遲 |
| 事實查詢無需人工介入 | 自動結案率，目標 45–55% |
| 回覆內容與後台資料一致 | 事實錯誤率，目標 0 |
| 排程零重複、零漏提醒 | 衝突數、漏提醒數 |
| 完整稽核軌跡 | 100% 訊息與核准可回溯 |

明確排除：資格審查、信用調查判讀、租金談判、租約條款解釋。

### 2.1 關鍵設計決定

**AI 只做分類與起草。「要不要自動送出」永遠由寫死的規則決定。**

不要讓模型自己判斷「這個我可以直接回」。原因：
- 規則可以被法務逐條審閱、版本控管、在法庭上解釋
- 模型的判斷邊界會隨版本更新漂移
- 出事時要能回答「為什麼這封被自動送出」，答案必須是規則編號，不是「模型認為可以」

## 3. 管道接入層

| 管道 | 接入方式 | 注意 |
|---|---|---|
| Email | AWS SES 收件 → SNS → 佇列，或 IMAP 輪詢 | 引用歷史、附件、自動回覆迴圈偵測 |
| 網站表單 | 直接寫入 API | 唯一能在送出前結構化收欄位的管道，優先引導 |
| SMS | Twilio Programmable Messaging | 加拿大號碼需完成 10DLC/短碼註冊；長度限制影響回覆設計 |
| WhatsApp | WhatsApp Business API | 24 小時客服視窗外只能發預先核准範本 |

### 3.1 統一訊息格式

```json
{
  "message_id": "msg_01H...",
  "thread_id": "thr_01H...",
  "channel": "email | webform | sms | whatsapp",
  "direction": "inbound | outbound",
  "contact": { "id": "ct_...", "name": null, "email": null, "phone": null },
  "body_text": "...",
  "received_at": "2026-08-01T14:22:03Z",
  "locale_detected": "zh-Hant | en",
  "consent": { "casl_basis": "implied_inquiry", "expires_at": "2027-02-01" }

```

### 3.2 CASL 同意基礎

加拿大反垃圾郵件法（CASL）管制商業電子訊息。租客主動詢問構成推定同意，回覆其詢問一般落在合理範圍。

**三類訊息的同意基礎不同，發送層必須分開檢查：**

| 類型 | 例子 | 基礎 |
|---|---|---|
| 回覆 | 回答空房詢問 | 推定同意（來自詢問） |
| 交易性 | 看房提醒、簽約時段確認 | 對方已預約，屬既有關係 |
| 行銷跟進 | 「新戶型開放了要不要看」 | 需獨立同意 ＋ 退訂機制 |

實際期限與例外請法務確認。

## 4. 事實檢索層

**這一層決定系統會不會胡說八道。回覆中的每一個數字、日期、單位編號，都必須來自這一層。模型不得推算或補值。**

### 4.1 可查詢的事實（唯一的 L3 自動回覆範圍）

| # | 事實 | 來源 |
|---|---|---|
| 1 | 戶型規格（面積、房數、陽台） | 靜態表 |
| 2 | 戶型月租 | 定價設定 |
| 3 | 空房清單（可依棟別、樓層、戶型篩選） | 單位狀態 = 可租 |
| 4 | 最早可入住日 | 單位可入住日欄位 |
| 5 | 押金規則與金額 | 押金設定 |
| 6 | 寵物政策與費用 | 寵物設定 |
| 7 | 車位餘額（各區） | 車位配額即時計算 |
| 8 | 車位候補順位 | 候補名單排序 |
| 9 | 車位、儲藏室、申請費等月費 | 費用設定 |
| 10 | 公設清單 | 靜態表 |
| 11 | 位置與交通 | 靜態表 |
| 12 | 可預約看房時段（只回時段，不含預約動作） | 排程引擎 |

**不在這張表上的，一律人工。**

### 4.2 查無資料時的行為

模型被明確指示：查詢為空或欄位未填時，回覆「這項我確認後回覆你」並轉人工，禁止推測。

這條規則要寫進 system prompt，**也要在後處理做程式校驗**——把草稿中所有金額與日期抽出，逐一比對是否存在於檢索結果，不符即攔下降級。這個校驗是規則，不是模型自評。

## 5. 自動化分級

| 級別 | 行為 | 適用 |
|---|---|---|
| **L3 全自動** | 直接送出 | §4.1 的 12 項事實查詢 |
| **L2 自動＋抽查** | 送出並寫入行事曆，每日抽 10% 複查 | 預約看房、改期、取消、預約簽約時段、行前提醒 |
| **L1 起草待審** | 進審核台，人工核准後送出 | 其餘全部：車位登記、續約、客訴、維修、提前解約、複雜或多戶詢問 |
| **L0 轉人工** | 不起草，直接指派 | §5.2 硬性攔截 |

### 5.1 規則編號

L3：R-2041 空房 · R-2042 租金 · R-2043 戶型 · R-2044 公設 · R-2045 位置 · R-2046 寵物 · R-2047 費用 · R-2048 車位餘額 · R-2049 候補順位 · R-2050 可預約時段

L2：R-2061 預約看房 · R-2062 改期 · R-2063 取消 · R-2064 預約簽約時段

L1：R-2081 車位登記 · R-2082 續約 · R-2083 客訴 · R-2084 維修 · R-2085 提前解約 · R-2099 其他

### 5.2 硬性攔截清單

以下無論設定為何一律轉人工，且在 AI 之前執行：

**R-101 資格審查與收入相關**
「你們收入門檻多少」「我領 AISH 可以租嗎」。
Alberta Human Rights Act 將**收入來源**列為受保護特徵。AI 自動回覆一旦被解讀成因補助身分而給出不同對待，就是白紙黑字的證據。

**R-102 無障礙與合理調整**
「我坐輪椅，需要靠電梯的車位」「我有服務犬」。
服務動物不是寵物，不適用寵物政策與費用；合理調整有法定程序義務。

**R-103 受保護特徵**
種族、族裔、宗教、性別、性傾向、婚姻狀態、家庭狀態、年齡、身心障礙、收入來源。
偵測到即轉人工，且**稽核紀錄不複製該內容**，只記錄「命中 R-103」。

**R-104 法律、投訴、爭議**
律師、Human Rights Commission、RTDRS、驅逐、押金爭議、損害求償。

**R-105 租約條款與議價**
租約條款、要求寄送租約、保留單位、任何偏離公告價的個別條件。
**注意**：單純預約簽約「時段」不在此列，走 L2；但租約文件仍須經 §8 的 Agent 閘門。

> 這五類請與律師或 RECA 顧問一起定稿再上線。以上為設計方向，不構成法律意見。

### 5.3 攔截實作

兩道關卡，都在 AI 之前：關鍵詞／正則表（中英雙語，含 AISH、ODSP、RTDRS 等縮寫），以及獨立的受保護特徵分類器。誤攔成本是專員多看一封信，漏攔成本是人權投訴——門檻往嚴格設。

## 6. 排程與提醒引擎

### 6.1 可預約時段

```
slot_template   週一–週五 09:00–18:00、週六 10:00–16:00（可設定）
slot_duration   帶看 30 分 · 線上簽約 45 分
buffer          每場之間 15 分
lead_time       最早可預約 = 現在 + 2 小時
horizon         最遠可預約 = 今日 + 30 天
blackout        假日、專員請假、單位維修期間
```

### 6.2 防衝突

寫入前取行事曆鎖，重新檢查該時段是否仍空。兩人同時預約同一時段時，後者收到「這個時段剛被預約，這是最接近的三個選擇」。

**這一點不能靠 AI 判斷，必須是資料庫層的交易。**

### 6.3 提醒規則

**提醒日 = 事件日的前一個工作日。**

```
prevBusinessDay(eventDate):
    d = eventDate - 1 天
    while d 是週末 或 d 在假日表:
        d = d - 1 天
    return d
```

推導結果：

| 事件日 | 提醒日 | 提前 |
|---|---|---|
| 週二–週五 | 前一天 | 1 天 |
| **週一** | **前週五** | **3 天** |
| 週六 | 週五 | 1 天 |
| 週日 | 週五 | 2 天 |
| 假日隔天 | 再往前推至最近工作日 | 視情況 |

發送時間預設 16:00，讓專員下班前就看到隔天（或下週一）要做什麼。

假日表可設定，預設為 Alberta 一般假日。**Heritage Day（8 月第一個週一）在 Alberta 屬選擇性假日，預設未列入，由你決定是否營業。**

### 6.4 兩種提醒，分開發

| 對象 | 內容 | 通道 |
|---|---|---|
| 租客 | 你預約的帶看／簽約時間、地點、需帶文件、改期連結 | 原詢問管道 |
| 專員 | 隔天（或下週一）的完整工作清單 | Email ＋ 後台 |

租客提醒屬交易性訊息；不要在裡面夾帶行銷內容，那會改變 CASL 的同意基礎。

## 8. 線上簽約與 Agent 核准閘門

### 8.1 流程

```
① 租客要求簽約
      ↓  L2 自動
② 系統排定簽約時段，寄出時段確認
      ↓  ※ 不附任何租約內容
③ 系統組裝簽約包裹（草稿）
      租金 · 押金 · 車位 · 儲藏室 · 起租日 · 期間 · 標準條款
      ↓
④ ★ Agent 帳號審核 ★  ← 唯一閘門，不可自動
      核准者、時間、核准當下的條件快照全部入稽核
      ↓  核准
⑤ 系統寄出電子簽署連結，有效期 72 小時
      ↓
⑥ 約定時段線上進行：專員在線說明，雙方簽署
      ↓
⑦ 已簽文件歸檔，單位狀態改為已租，車位由候補轉正式
```

### 8.2 為什麼閘門在第 ④ 步

時段可以自動排，因為排錯了可以改期。租約文件送出即不可逆——一旦租客簽了，你就受條款拘束。所以閘門要放在文件離開系統之前，不是之後。

### 8.3 核准前檢查表

Agent 核准畫面必須逐項確認：

- [ ] 租金、押金、費用與後台一致
- [ ] 車位與儲藏室配置已確認且庫存足夠
- [ ] 租客資格審查已由專人完成（**不可由系統代勞**）
- [ ] 租約條款無個別修改，或修改已另行核准
- [ ] 起租日與單位可入住日相符

### 8.4 稽核

```json
{
  "signing_id": "sgn_...",
  "unit_id": "378-519",
  "contact_id": "ct_...",
  "scheduled_at": "2026-08-03T15:00:00-06:00",
  "package_snapshot": { "rent": 1850, "deposit": 1850, "parking": "地下378", "term_months": 12 },
  "approved_by": "agent_chris",
  "approved_at": "2026-08-01T11:04:22Z",
  "link_sent_at": "2026-08-01T11:04:25Z",
  "link_expires_at": "2026-08-04T11:04:25Z",
  "signed_at": null
}
```

`package_snapshot` 記錄核准當下的條件。日後爭議時，能證明簽的是哪一版。

### 8.5 電子簽章

Alberta 的 Electronic Transactions Act 一般承認電子簽章的效力，但實務上要注意簽署流程的**身分驗證**與**意思表示紀錄**是否足以在爭議時舉證。選 e-sign 供應商時確認其稽核軌跡（IP、時間戳、驗證方式）與資料存放地區。具體要求請法務確認。

## 9. 稽核與隱私

### 9.1 每封送出訊息留存

```json
{
  "outbound_id": "out_...",
  "in_reply_to": "msg_...",
  "routing_decision": "L3_AUTO",
  "rule_id": "R-2041",
  "rule_version": "2026-08-01",
  "intent": "availability",
  "intent_confidence": 0.94,
  "facts_used": [
    { "key": "vacant.2A", "value": 12, "snapshot_at": "2026-08-01T14:22:05Z" },
    { "key": "rent.2A", "value": 1850, "snapshot_at": "2026-08-01T14:22:05Z" }
  ],
  "model": "claude-sonnet-4-6",
  "prompt_version": "v1.1",
  "draft_edited_by_human": false,
  "sent_at": "2026-08-01T14:22:11Z"
}
```

`facts_used` 是關鍵——事後有人問「當時為什麼報這個價」，能直接指出那一刻後台的值。

### 9.2 Alberta PIPA

- 蒐集目的明示，僅蒐集必要範圍
- 表單與自動回覆頁尾附隱私聲明連結
- 支援單一聯絡人資料的查閱、更正與匯出
- 送往第三方 LLM API 屬揭露行為，須在隱私政策說明；評估是否需要資料處理協議與地區限制

### 9.3 自動化揭露

自動回覆頁尾明確標示訊息由自動系統產生，並提供轉真人的方式。這既是誠信問題，也降低「租客以為在跟人談」的爭議。

```
                 approved_by, approved_at, link_sent_at, link_expires_at, signed_at)
blocked_events  (id, message_id, rule_id, blocked_at)   ← 不儲存訊息原文
```

## 11. 技術選型

| 層 | 建議 | 理由 |
|---|---|---|
| 訊息佇列 | SQS / Redis Streams | 削峰與重試 |
| 應用 | Node.js 或 Python ＋ Postgres | JSONB 適合存 meta；行事曆需要交易鎖 |
| LLM | Claude（分類用小模型，起草用 Sonnet 級） | 成本結構不同，分開配置 |
| 排程 | Postgres ＋ cron worker | 提醒推算需要假日表 join，放資料庫比放程式碼好維護 |
| 電子簽章 | 第三方 e-sign 服務 | 稽核軌跡與法遵由供應商承擔 |
| 前端 | 現有後台加分頁 | 專員不必學第二套系統 |

**不建議一開始上 RAG。** 事實來源是結構化資料庫，直接查詢比向量檢索更準也更好稽核。RAG 留給租約條款、社區規則這類長文件，且只在 L1 起草時使用。

## 12. 導入階段

**Phase 1 — 影子模式（2–4 週）**
全流程跑但不送出。專員照常回覆，系統在旁起草。比對差異，校準規則與 prompt。上線前就知道誤判率。

**Phase 2 — L3 開放（法務審閱後）**
只開放 §4.1 事實查詢自動送出。硬性攔截全開。每日檢視全部自動送出訊息。

**Phase 3 — 排程開放**
看房預約、改期、取消、提醒自動化。每日工作清單上線。此時要確認防衝突的交易鎖在併發下正確。

**Phase 4 — 線上簽約**
簽約時段自動排 ＋ Agent 核准閘門 ＋ 電子簽署。先跑十份人工並行對照。

**Phase 5 — 多語言與行銷跟進**
中英雙語。跟進訊息須先解決 CASL 獨立同意。

## 13. 監控指標

| 指標 | 警戒 |
|---|---|
| 事實錯誤率 | > 0 即停用該意圖 |
| 硬性攔截命中率 | 突然下降代表偵測失效 |
| 排程衝突數 | > 0 即檢查交易鎖 |
| 漏發提醒數 | > 0 即檢查假日表與 cron |
| 簽約審核逾 24 小時 | > 2 件 |
| L1 審核台積壓 | > 20 封 |
| 人工修改草稿比例 | > 40% 代表該意圖不該在 L3 |
| 平均首次回覆時間 | > 15 分鐘 |

## 14. 風險登錄

| 風險 | 影響 | 緩解 |
|---|---|---|
| 自動回覆給出錯誤租金 | 可能構成報價 | 事實校驗層 ＋ 頁尾「以正式租約為準」 |
| 受保護特徵漏攔 | 人權投訴，書面證據 | 雙重偵測、寧可誤攔、影子模式校準 |
| 排程重複預約 | 兩組人同時到場 | 資料庫交易鎖，不靠 AI 判斷 |
| 假日表未更新 | 提醒發在假日，等於沒發 | 每年 12 月排程檢查任務 ＋ 漏提醒監控 |
| 簽約連結誤發 | 不可逆 | Agent 閘門 ＋ 72 小時失效 ＋ 撤回機制 |
| LLM 服務中斷 | 回覆停擺 | 降級為固定罐頭訊息「已收到，專員將盡快回覆」 |
| Prompt 更新造成行為漂移 | 已審閱的行為改變 | prompt 版本化，變更需重跑影子模式回歸測試 |
