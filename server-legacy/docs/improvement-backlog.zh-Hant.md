# Baydo Pointe 系統 — 優化建議

日期 2026-07-31 · 對應目前八個原型與資料庫綱要

---

## 0. 先修的三件事

這三項不修的話，其他優化做了效果有限。

**① 前端輪詢當稽核，會漏。**
現在的變更紀錄靠每 60 秒掃描一次，頁面關著的時候什麼都記不到。稽核必須在後端每次寫入時記錄，這是唯一可靠的做法。備份同理，要伺服器排程，不是靠有人開著頁面。

**② 前端藏功能不是權限。**
Agent 打開開發者工具就能改自己的角色、讀到所有設定。每個 API 都要在後端檢查呼叫者的角色，這件事沒有捷徑。

**③ 車位與時段的併發沒擋住。**
兩個人同時登記最後一個車位，前端各自檢查都會過。SQL 綱要裡的 `SELECT ... FOR UPDATE` 和 `EXCLUDE USING gist` 就是為此準備的，實作時務必用上。

## 1. 資料模型

### 1.1 單位狀態需要更細

現在只有 available / held / leased。實際上會遇到：

| 缺的狀態 | 情境 |
|---|---|
| `notice_given` | 現住戶已通知搬離，還沒空但可以開始帶看 |
| `turnover` | 已搬空，整理中，不能入住 |
| `offline` | 維修、水損、消防問題 |

沒有 `notice_given` 就沒辦法提前招租，這是空置期最容易省下來的地方。

### 1.2 保留（hold）要有到期時間

現在 held 是永久的。實務上保留應該有明確期限（例如 48 小時），到期自動釋出並通知專員。不然單位會被「保留」到忘記，變成隱形空置。

建議加 `held_until timestamptz` 與 `held_for_contact_id`。

### 1.3 名單與聯絡人要合併

CRM 的 leads 和 contacts 現在是兩套。同一個人先詢問、後成為租客、再續約，應該是同一筆 contact，leads 只是他在某個時間點的階段。分開會造成重複資料與追蹤斷裂。

建議：`contacts` 為主體，`leads` 改成 `lead_stages`（contact_id + unit_interest + stage + timestamps）。

### 1.4 加 `unit_availability` 視圖

空房查詢現在每次都要 join 好幾張表算。建議做成物化視圖，每次單位或租約變動時刷新——AI 自動回覆的第一大查詢就是這個，值得優化。

## 2. 業務流程

### 2.1 車位缺口需要政策，不只是排隊

330 戶對 222 位，缺 108。先到先得規則清楚，但會產生一個結構問題：**開租初期全部被搶光，之後所有新租客只能候補，而候補幾乎不會動**（車位跟著租約走，租客不搬就不會釋出）。

三個可考慮的方向：

1. **保留配額**：留 15–20 個不進先到先得池，作為大坪數或長約的談判籌碼。一旦全放進池子就拿不回來。
2. **車位獨立計費與獨立終止**：租客不開車時可以退，池子才會流動。目前已建議車位獨立成約，這個設計要保住。
3. **候補通知機制**：候補者長期沒消息會流失。至少每季通知一次目前順位，讓人知道還在排。

流失原因統計裡「車位不足」如果持續往上，那是結構問題，不是業務問題。

### 2.2 帶看轉換沒有量測

現在有帶看排程，但沒有記錄結果。建議在 `events` 加 `outcome` 欄位：到場 / 未到場 / 有意願 / 無意願 / 當場送件。

沒有這個就答不出兩個關鍵問題：哪些單位帶看很多但沒人租（定價或狀況有問題）、哪個來源的客人最常放鳥（廣告投錯地方）。

### 2.3 未到場（no-show）要處理

帶看 no-show 在租屋業很常見。建議：提醒訊息加一鍵確認、連續兩次 no-show 的名單標記、時段釋出後自動開放給其他人。

### 2.4 續約流程還沒做

目前整套系統都在處理「新租客」，但續約才是省錢的地方——換一個租客的成本（空置＋整理＋招租）遠高於留住一個。

建議補：租約到期前 90 天自動生成續約任務、續約報價（可與新租不同）、續約意向調查、不續約的原因記錄。

### 2.5 遷出流程完全沒有

退租通知、遷出檢查報告、押金結算與退還、鑰匙回收——這些一個都沒有。Alberta 對押金退還有時限與扣款證明的要求，做不好會直接變成爭議。

**這一塊建議優先於再加新功能。** 你們的第一批租客大約一年後就會走到這一步。

## 3. AI 與自動化

### 3.1 事實層要加版本戳

現在 `facts_used` 記了值，但沒記那份定價是哪個版本。建議一併記 `pricing_profile_id`，爭議時可以直接指出「當時生效的是 8 月版定價」。

### 3.2 加一層「答非所問」偵測

租客回「你沒回答我的問題」是最有價值的訊號，但現在沒抓。建議偵測這類回覆並自動標記該意圖，累積到門檻就把它降級回人工。

### 3.3 影子模式的比對要能量化

架構文件寫了影子模式，但沒定義怎麼算通過。建議設明確門檻：事實錯誤 0 件、人工改寫比例低於 20%、硬性攔截無漏網——三項全過才開放該意圖自動送出。

### 3.4 罐頭降級訊息要先寫好

LLM 掛掉時的備援訊息現在還是待辦。這個要在上線前就準備好並測過，不然真的斷線時系統會靜默失敗。

## 4. 效能

| 項目 | 現況 | 建議 |
|---|---|---|
| 空房查詢 | 每次重算 | 物化視圖 + 觸發器刷新 |
| 車位餘額 | 每次 count | 在 pool 存 `assigned_count`，用觸發器維護 |
| 每日工作清單 | 即時組合多來源 | 每日凌晨預先產生，當天只讀 |
| 稽核紀錄 | 單表無限成長 | 按月分割（partition），舊資料轉冷儲存 |
| 訊息全文搜尋 | 無 | `tsvector` + GIN 索引 |
| 快照備份 | 全量 | 改增量，或至少壓縮後存物件儲存 |

330 戶的規模這些都還撐得住，但如果之後接第二個案子就會開始有感。

## 5. 合規與風險

### 5.1 資料保留期限沒定

Alberta PIPA 要求只保留必要期間。現在名單、訊息、稽核紀錄都是無限期保存。建議明訂：

| 資料 | 建議保留 |
|---|---|
| 未成交名單 | 最後聯絡後 12 個月 |
| 訊息往來 | 3 年 |
| 租約與檢查報告 | 租約結束後 7 年 |
| 稽核紀錄 | 7 年 |
| 快照備份 | 30 天 |

**期限要寫成自動清除工作，不是寫在文件裡就算。**

### 5.2 送第三方 API 的資料要說明

租客訊息會送到 LLM API，這在 PIPA 下屬於揭露行為，隱私政策必須寫明。另外要確認資料處理協議與存放地區。

### 5.3 稽核紀錄要唯讀

現在 Admin 可以透過回檔改掉稽核紀錄。真正的稽核表應該是唯讀附加，連 Admin 也不能改——不然出事時它證明不了任何事。

### 5.4 職務分離還沒決定

Agent 目前可以核准自己送的件。你已確認接受，但至少要做到：核准紀錄明確標示送件人與核准人相同，讓事後查得出來。人手多了以後再考慮強制分離。

### 5.5 服務動物的處理要寫進 SOP

系統會攔截並轉人工，但接手的人要知道怎麼做。這需要一份書面流程，不是靠專員臨場判斷——這類請求處理錯了就是人權投訴。

## 6. 使用者體驗

**行動裝置**：專員帶看時在現場用手機。目前介面雖然響應式，但沒有針對「站在走廊上單手操作」設計。帶看報到、記錄結果、拍照上傳這幾件事應該做成大按鈕的手機專用流程。

**離線**：停車場和電梯沒訊號。至少要讓已載入的行程在離線時看得到。

**通知**：現在提醒只寫進資料庫，沒有實際推播。專員不會一直開著頁面。

**單一入口**：目前八個工具各自獨立，專員要在分頁間切換。上線前應整合成一個應用，共用導覽列與登入狀態。

## 7. 建議順序

**第一階段（上線前必須）**
1. 後端權限檢查
2. 後端稽核與備份
3. 車位與時段的併發鎖
4. 律師版租約與所有文件範本
5. 遷出與押金結算流程
6. 罐頭降級訊息

**第二階段（上線後三個月內）**
7. 續約流程
8. 帶看結果記錄
9. 資料保留自動清除
10. 名單與聯絡人合併
11. 手機專用帶看流程

**第三階段（有數據之後）**
12. AI 影子模式與逐步開放
13. 效能優化（物化視圖、分割表）
14. 來源成效分析與廣告預算調整
15. 車位政策依實際流失數據調整

## 8. 目前八個原型的狀態

| 工具 | 用途 | 缺什麼 |
|---|---|---|
| 登入 | 帳號、忘記密碼、重設 | 後端驗證、Argon2id、真的寄信 |
| 出租後台 | 定價、車位、單位總覽 | 併發鎖、單位狀態細分 |
| 排程 | 每日清單、提醒、簽約閘門 | 實際推播、no-show 處理 |
| AI 收件匣 | 分類、起草、路由 | 真的接管道、影子模式 |
| 合約組裝 | 訪談、變數、費用告知 | 律師範本 |
| 文件庫 | 範本、填寫、簽核 | PDF/Word 後端解析、電子簽章串接 |
| CRM | 名單、帶看行程、漏斗 | 與 contacts 合併、帶看結果 |
| 變更紀錄 | 稽核、備份回檔 | 移到後端 |

八個都是原型。共同的缺口是同一個：**沒有後端**。
