# 付款

## 兩件不是技術的決定

### 1. 手續費差 $164,000 一年

$1,450 的租金：

| 方式 | 每筆 | 330 戶一年 |
|---|---:|---:|
| 信用卡 | $42.35 | **$167,706** |
| EFT／預授權扣款 | $11.85 | $46,926 |
| Interac e-Transfer | $1.50 | $5,940 |
| 支票 | $0 | $0 |

系統把費率和**「誰吸收」**做成每個方式各自的設定：

- `absorb` — 物業當費用吃掉
- `surcharge` — 加在租客要付的金額上

**加收在加拿大 2022 起信用卡是合法的**，但受卡組織規則和上限限制，而且**必須在付款前揭露**。開之前請確認當下的規則。

租金是債務，所以加收不是調漲租金、不需要通知期。但它仍然改變了某人要付的金額，**不該無預警出現**——所以租客端在選擇之前就看得到每個方式的費用，不是在確認頁才看到。

### 2. 押金必須進信託帳戶

押金是信託負債：`1020` 銀行對 `2100 + 2110` 負債，儀表板每次檢查兩邊相等。

**但金流服務商預設把所有錢撥到同一個帳戶。** 押金落進營運帳戶的話：

```
2100 負債增加了
1020 信託銀行沒有增加
→ 信託對帳當場失衡，而且沒有東西說明為什麼
```

所以資料庫層擋住：

```
ERROR: A security deposit has to settle into the trust account (1020),
       not 1010. The trust reconciliation compares 1020 against the
       deposit liability, and money landing anywhere else breaks it
       silently.
```

有一個獨立的 `deposit_trust` 付款方式，撥款到 1020。**或者押金收進營運帳戶後手動轉撥並記錄**——但那要有人記得。

## 沖銷順序：這個有法律後果

**租金優先，最舊的先沖。**

不是隨便訂的。租客繳了租金，如果被系統拿去沖銷一筆他正在爭議的損壞賠償，**他現在就是租金欠繳**——而租金欠繳是可以終止租約的理由，爭議中的損壞賠償不是。

```
rent → parking → storage → pet → utilities → late_fee → damage → other
```

**租客可以指定沖銷哪一筆，而那個指定會被記錄成「租客要求的」。**

「他要求的」和「我們決定的」在被質疑時是兩件事。

---

## 線上和支票是同一張表

租客線上付、會計輸入支票，都進 `payments`。

**租客的帳單不該在意錢是怎麼來的，而要看兩個地方的對帳是會漏掉一邊的對帳。**

---

## 收到 ≠ 到帳

| 方式 | 可撤銷天數 |
|---|---|
| 信用卡 | 120 |
| 預授權扣款 | 90 |
| 支票 | 30 |
| e-Transfer | 0（接受後不可撤） |
| 現金 | 0 |

支票是**到達當天輸入，不是兌現當天**——但狀態是 `authorised` 不是 `settled`。

畫面會提醒：「一張支票在 30 天內都還可能退票。」

---

## 退票

**不是刪除。** 付款發生過、退票也發生過，兩件都是歷史的一部分。

刪掉的話，租客手上會有一張系統不認得的收據。

退票會把相關的收費單狀態改回 `open`，並註明：

> 退票手續費是另一筆有自己依據的收費，不是這一筆的調整。

---

## 溢繳

多繳的錢是**預收租金，不是意外之財**。

它掛在負債裡，直到有一筆收費可以沖銷。現在就認列成收入，等於承認了一個還沒發生的月份的租金。

---

## 還沒接的

**金流服務商還沒接。** 目前記錄的是「意圖」——資料結構、費用計算、信託路由、沖銷順序都好了，但沒有真的向誰收費。

接的時候要注意：

**Webhook 會重送。** `processor_ref` 有唯一索引擋住，**收兩次錢比漏一次糟**。

**押金要獨立的 settlement account**，不然信託分離就是假的。
